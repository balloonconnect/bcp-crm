# Monitoring and Observability

Structured logs with request/studio/user correlation, per-service
health checks across all 8 services named in the brief, a platform
health dashboard, configurable alert rules, a real public status page
(replacing a documented placeholder), incident history, and service
uptime tracking — with a genuinely enforced "never log" list rather
than a policy nobody checks. Built across `@bcp/observability`
(registries, aggregation rules, alert-condition evaluation, uptime
math, the redaction list — all pure) and `apps/api`'s
`health-checks.service.ts`, `alerts.service.ts`, `incidents.service.ts`.

## Never log — enforced at the root logger, not by convention

`NEVER_LOG_PATHS` maps the five categories named in the brief
(passwords, OTPs, access tokens, payment secrets, sensitive photo
URLs) to the actual field-name patterns this codebase's request/
response payloads use for them. This list is wired directly into
`@bcp/logger`'s pino instance via its `redact` option — every logger
anywhere in this platform (`logger.child(...)`) inherits the same
redaction automatically. A service can't accidentally log a password
by forgetting to redact it locally, because the root logger never
passes a matching field through in the first place. Redacted fields
show `"[Redacted]"` rather than being silently dropped, so a log line
still reveals *that* a sensitive field was present (useful for
debugging) without ever printing its value.

## Structured logs with request/studio/user correlation

Fastify's own native `genReqId`/`requestIdHeader` options (configured
in `app.ts`) handle "Request IDs" — reusing an inbound `X-Request-Id`
when one exists (so a request already traced upstream keeps the same
ID through this API) rather than layering a second, competing ID
mechanism on top. `request-logging.ts` enriches Fastify's own
already-existing per-request child logger with `studioId`/`userId`
once auth resolves, so every log line from that point in a request
carries full correlation without every route handler needing to
remember to add it.

## The 8 monitored services, checked honestly

`MONITORED_SERVICES` distinguishes services genuinely checkable with a
live network call (database via `SELECT 1`, Redis via a real `PING`,
storage via a new `StorageClient.headBucket()` added specifically for
this, queue via a stale-job-count query) from ones deliberately
checked only as "is it configured" (AI provider, WhatsApp, payment
provider) — a live call to Claude, WhatsApp, or Razorpay on every
health-check cycle would burn real quota and cost purely to confirm
the platform is up; the honest, useful signal is whether the
credentials a feature needs are actually present, which is exactly
what would make that feature unhealthy the moment someone tries to use
it anyway.

## Platform health dashboard

`aggregateOverallHealth()` — the platform is only ever as healthy as
its worst service; any unhealthy service makes the whole platform
unhealthy, any degraded service (nothing worse) makes it degraded.
Never averaged, which could hide a genuinely broken service in the
noise. `apps/platform-admin`'s `/health` page (already existed as a
narrower, honest scaffold — "a real deployment would add a Redis ping
and a queue-depth check here too," its own prior comment said) now
shows all 8 services individually, with alert-rule management and
incident history alongside it.

## Alert rules — condition, not a single blip

An `AlertRule` only fires once its most recent N consecutive checks
(its own configured threshold) all reach or worsen past the trigger
status — never on one transient blip. A rule already actively firing
is never re-triggered while the underlying problem persists; once the
condition clears, the open alert is automatically marked resolved.

## Public status page — replacing a real, honest placeholder

`apps/status-web` previously showed literally: "scaffold placeholder.
Business features are built in a later phase." This is that phase —
a real page polling `/status/public` (unauthenticated, deliberately,
since a status page is only useful if anyone can see it) for current
per-service status, 90-day uptime percentages, and incident history.
The public endpoint reads the most recently *persisted* health check
per service rather than running live checks on every anonymous page
view, which would let public traffic drive real health-check load —
health data is generated by the platform-admin dashboard view (and,
in a real deployment, should also run on a schedule via the queue
system from Prompt 44, not yet wired to a recurring job in this pass).

## Incident history

`Incident`/`IncidentUpdate` follow the standard status-page convention
— a timestamped, append-only timeline of updates within one incident,
rather than overwriting a single description field each time. Creating
an incident always posts its first update in the same step; posting an
update also moves the incident's own current status forward, so the
header and the timeline can never contradict each other.

## Two real bugs caught during this pass

1. A first draft of the request-ID/logging plugin redeclared Fastify's
   own already-existing `request.log` type, which would have fought
   Fastify's native per-request logger and ID generation rather than
   extending it — caught before it shipped and rewritten to enrich the
   existing mechanism instead of replacing it.
2. The public status endpoint's first draft ran live health checks
   (with real database writes) on every anonymous page view — a public
   endpoint whose load scales with public traffic driving real
   infrastructure checks is a real design smell, caught and fixed to
   read persisted history instead.
